**Data:** 15 de setembro de 2026
**Resultado geral:** aprovado após correção — captura específica da janela do FNAF validada com o jogo iniciado manualmente
**Jogo:** Five Nights at Freddy's 1
**Executável:** `data/games/FNAF1/FiveNightsatFreddys.exe`
**Modo do Bridge:** `dry-run=true`
**Input físico:** não utilizado

Validar o caminho real do Beta 2:

```text
FNAF 1 no Windows
  -> Host Bridge C#/.NET
  -> captura de janela
  -> WebSocket autenticado
  -> Core no Docker
  -> dashboard do Beta 2
```

## Correções implementadas e reteste

Após a execução inicial, foram feitas as seguintes correções no Host Bridge:

- adição de `Windows.Graphics.Capture` como caminho preferencial de captura,
  usando `CreateForWindow` para HWND e `CreateForMonitor` para HMONITOR;
- dependência restaurável do Windows SDK/WinRT no próprio projeto, sem exigir
  que o SDK esteja instalado globalmente na máquina;
- `--screen` passou a capturar o monitor primário pelo compositor do Windows,
  evitando `Graphics.CopyFromScreen` quando a sessão GDI não possui um DC
  utilizável;
- fallback preservado: `PrintWindow` para janelas e GDI para desktop, com
  registro explícito da estratégia usada;
- falha de WGC por alvo é registrada uma vez e não provoca tentativa de
  reinicialização a cada frame;
- seleção do monitor não é mais tratada como HWND no fallback;
- catálogo de tela cheia foi substituído por uma região de monitor válida,
  mantendo `safe_capture` no modo `--screen`.

## Falha visual observada

O arquivo `data/bridge/preview.png` foi inspecionado após a captura e contém
uma imagem completamente preta. Isso significa que a falha não está no
WebSocket nem no dashboard: o conteúdo já chega preto ao Core.

Foram observados dois comportamentos distintos:

1. `--screen`: a captura inteira da área de trabalho falhou imediatamente em
   `Graphics.CopyFromScreen` com `Win32Exception (6)`.
2. Captura específica da janela: `PrintWindow` conseguiu produzir PNGs válidos
   e o transporte os aceitou, mas a superfície gráfica do FNAF 1 em tela cheia
   foi renderizada como preta.

## Reteste com inicialização manual do FNAF

O jogo foi iniciado manualmente pelo usuário e não foi iniciado, encerrado ou
controlado pelo processo de teste. O processo observado foi:

- PID `35648`;
- título `Five Nights at Freddy's`;
- HWND `1182856`;
- janela visível de `1296x759`.

Durante a primeira tentativa, o Bridge encontrou o jogo no desktop interativo,
mas a validação do HWND era feita a partir de um desktop auxiliar da sessão de
execução. Isso fazia `IsWindow` retornar falso e produzia a mensagem incorreta
de que a janela havia deixado de ser válida.

Foi corrigido o Host Bridge para:

- enumerar também o desktop de entrada do Windows com
  `OpenInputDesktop`/`EnumDesktopWindows`;
- deduplicar janelas descobertas pelo desktop atual e pelo desktop interativo;
- preservar a validação forte quando o HWND pode ser consultado diretamente;
- usar, no caso entre desktops, a combinação de HWND selecionado, PID ainda
  vivo e limites salvos da seleção para entregar a captura ao WGC.

Após recompilar, a execução normal do Bridge selecionou automaticamente o
FNAF, conectou ao Core e capturou a janela por `Windows.Graphics.Capture` sem
fallback preto:

| Evidência | Resultado |
| --- | --- |
| Sessão Bridge/Core | `hello_ack` aceito; WebSocket autenticado |
| Captura | `capture.graphics_capture`, alvo `window` |
| Frames | `21` frames registrados no log para o PID `35648` durante o reteste |
| Resolução enviada | `1227x720` |
| Tamanho dos PNGs | entre `749336` e `749499` bytes |
| Core | `735` frames acumulados no status; último frame sem erro |
| Dashboard | HTTP `200`, página com `15746` bytes |
| Preview do Core | HTTP `200`, `image/png`, `749386` bytes |
| Conteúdo visual | jogo real em `3 AM`, `Night 1`, `Power left: 66%` |
| Input físico | não utilizado; `dry_run=true` |

O preview final foi inspecionado visualmente e contém a sala do FNAF, os
controles `DOOR`/`LIGHT`, a energia e o relógio do jogo. Portanto, a hipótese
de que o problema era necessariamente o Bridge iniciar o executável não se
confirma neste reteste: o jogo iniciado manualmente foi capturado corretamente
pela janela específica.

## Conclusão atualizada

O Beta 2 está aprovado para o caminho de captura visual específica do FNAF em
modo `dry-run`:

- o jogo real foi iniciado manualmente;
- o Game Profile `fnaf1` foi aplicado;
- a janela real foi localizada no desktop interativo;
- o Bridge conectou ao Core Docker;
- `Windows.Graphics.Capture` entregou pixels úteis do HWND;
- frames foram confirmados pelo WebSocket e armazenados pelo Core;
- o dashboard e o endpoint de preview refletiram dados reais;
- o preview foi visualmente validado como conteúdo do jogo, não como imagem preta;
- o Bridge encerrou sem input físico e o processo do jogo permaneceu aberto.

Esta validação aprova a fundação de entrada visual do Beta 2. Ela ainda não
aprova percepção semântica, áudio live ou execução de teclado/mouse: esses itens
continuam pertencendo aos Betas 3–6.

## Intervenção manual necessária

Para este teste específico, nenhuma intervenção manual adicional é necessária:
o jogo já foi aberto pelo usuário, o Bridge foi executado em `dry-run` e o
processo permaneceu aberto ao final.

Para repetir o teste em outra sessão, a única pré-condição operacional é abrir
o FNAF em uma sessão Windows interativa e deixá-lo chegar a uma tela renderizada
(menu ou início da noite). Depois disso, o Bridge pode selecionar o perfil e a
janela sem iniciar o executável por conta própria.
